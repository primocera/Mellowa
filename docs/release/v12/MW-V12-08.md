# MW-V12-08 · Turn the capped beta into a real willingness-to-pay experiment

- **Run after:** MW-V12-07
- **Primary risk removed:** Technical quality is high, but recurring consumer value and retention are not yet proven.

## Prompt

Implement the smallest privacy-safe measurement system needed to decide whether Mellowa should scale beyond a capped beta.

Use docs/beta-scorecard.md as the canonical decision framework. Do not invent success after seeing data.

Required metrics and definitions:
1. Activation:
   - completed onboarding;
   - created free sample;
   - opened the sample;
   - understood how to adjust.
2. Repeat value:
   - day-2 return;
   - day-3 return;
   - day-7 return;
   - adjust preview -> apply;
   - completed-item preservation;
   - undo use;
   - weekly reflection open/completion;
   - carry-forward use.
3. Commercial:
   - sample -> plan selection;
   - checkout start;
   - trial start;
   - trial -> first charge;
   - first renewal;
   - cancellation timing;
   - refund;
   - support cost per paying user.
4. Safety/quality:
   - safety redirect rate by broad category;
   - provider failure;
   - plan repair;
   - user feedback that a plan did not fit.

Privacy rules:
- Never send check-in text, allergies, mood notes, plan contents, email or direct identifiers to analytics.
- Use a closed event enum and allowlisted property keys.
- Store only the minimum aggregation needed for the scorecard.

Decision rules:
- Keep predeclared numerators, denominators, windows and cohort minimums.
- Cohorts under five display "insufficient data", never 0%.
- Expansion defaults to BLOCKED until every required metric has enough data.
- Define stop, investigate, continue and expand thresholds before launch.
- Do not optimize for engagement through shame, streaks or notifications without consent.

Build an owner-facing scorecard that shows definitions and data freshness. Add contract tests proving every event and property is allowlisted and sensitive data is rejected.
