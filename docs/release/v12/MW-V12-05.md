# MW-V12-05 · Make key rotation and restore readiness operationally testable

- **Run after:** MW-V12-04
- **Primary risk removed:** The first real key rotation or database restore could occur during an incident with no measured recovery time.

## Prompt

Improve Mellowa resilience documentation and automated readiness checks without rotating real secrets or restoring production.

Scope:
- docs/runbooks/key-rotation-and-backup.md
- release manifest owner-evidence model
- readiness checks that can safely verify configuration presence
- non-production restore verification scripts/tests

Requirements:
1. Define separate procedures for Supabase keys, Stripe webhook secret, Stripe API key, Resend key, cron secret and application session secret.
2. Each procedure must include owner, preconditions, dependency order, overlap window, verification, rollback and evidence.
3. Never print secret values. Presence/fingerprint comparison must be one-way and safe.
4. Define isolated restore verification for a non-production target.
5. The restore checklist must verify:
   - expected row counts;
   - no orphaned user IDs;
   - ownership/RLS behavior;
   - reminder consent/version;
   - allergy and dietary fields;
   - Stripe customer/subscription mapping;
   - deletion tombstones;
   - plan versions and snapshots.
6. State explicitly what a database restore does not restore: Stripe objects, secrets, cron schedules, suppression lists and already-sent mail.
7. Treat restoration of deleted personal data as a data-protection incident requiring review, not a normal rollback.
8. Record desired RTO/RPO separately from tested RTO/RPO. Blank tested values must never be presented as achieved targets.
9. Add tests that fail if required runbook sections, verification rows, abort conditions or evidence fields disappear.

Do not mark owner evidence complete. Finish with the exact safe owner steps required to perform the drill and the stop conditions that prevent production damage.
