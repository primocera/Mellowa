1 · WELCOME EMAIL — PASS
--------------------------------------------------------------------------
  welcome:6d5ea45e…   sent   provider ef753e9a…   2026-07-27 12:00:46

Note: this required a SECOND fix. The Supabase "Confirm signup" template used
the default {{ .ConfirmationURL }}, which confirms the email via Supabase's
own /auth/v1/verify BEFORE redirecting to /auth/callback with ?code=. When the
PKCE exchange failed (different browser/device/cleared cookies) the callback
returned at its link_expired branch — above both the welcome send and the
consent write. Result: accounts confirmed in auth.users with null
last_sign_in_at, no welcome mail, no consent row, and a page claiming the link
had expired. Users 266ba450… and 5b261b9a… were both in that state.

Template changed to the token_hash form on 2026-07-28; verifyOtp needs no
browser cookie, so cross-device confirmation now works. Recorded in the
callback route because it is dashboard config with no repo representation.

2 · UNSUBSCRIBE WRITES THE CONSENT STATE — PASS
--------------------------------------------------------------------------
Reminder mail delivered via a manual cron trigger:

  POST /api/cron/daily-reminders → 200
  {"ok":true,"sent":1,"nudged":2,"scanned":1,"invalid_timezones":0,
   "skipped":{...all zero},"truncated":false}

Clicked "Turn reminder emails off" in the delivered mail. Profile after:

  user 2e560d26…   reminders_opt_in false   reminders_paused true
                   reminder_time null       timezone Europe/Ljubljana

This is the first time one-click unsubscribe has ever worked. Until commit
dc46c70 the route updated `profiles` keyed by `id` — a table that does not
have reminders_opt_in, reminders_paused or reminder_time at all. PostgREST
rejected the write, the user got the failure page, and the scheduler's view
was untouched. No test caught it because none asserted that the write lands
where the scheduler reads.

3 · SUPPRESSION IS ENFORCED, NOT MERELY RECORDED — PASS
--------------------------------------------------------------------------
The cron's own filter, run as a query:

  reminders_opt_in = true AND reminder_time IS NOT NULL
    AND reminders_paused = false          →  0 rows

Confirmed live by re-firing the cron after the unsubscribe:

  {"ok":true,"sent":0,"nudged":0,"scanned":0,...}

scanned:0 is the load-bearing number. The account is excluded at the database
query level, not filtered out downstream. Item 2 alone would only have proven
that a row changed.
